## FINDING (Low–Medium): Internet-exposed HashiCorp Vault running outdated version — `vault.algolia.net`

**Asset:** `vault.algolia.net` — matches in-scope `*.algolia.net`. Resolves to public AWS IPs
(`52.210.217.151`, `99.80.166.212`, `34.250.96.126`). Confirmed reachable from an arbitrary internet host.

**What was observed (read-only, unauthenticated):**
```
$ curl https://vault.algolia.net/v1/sys/health
{"initialized":true,"sealed":false,"standby":false,"performance_standby":false,
 "replication_performance_mode":"disabled","replication_dr_mode":"disabled",
 "server_time_utc":1790331319,"version":"1.16.2","enterprise":false,
 "cluster_name":"vault-cluster-0d3c6369","cluster_id":"9075ba06-d9e3-1e04-6ca5-e…"}

$ curl https://vault.algolia.net/v1/sys/seal-status
{"type":"shamir","initialized":true,"sealed":false,"t":2,"n":18,"progress":0,
 "version":"1.16.2","build_date":"2024-04-22T16:25:54Z","migration":false,
 "cluster_name":"vault-cluster-0d3c6369","cluster_id":"9075ba06-…","storage_type":"raft","recovery_seal":false}
```
`/ui/` returned 404 (no web UI served on that path), but the **Vault HTTP API is live and internet-reachable**.

**Why it matters:**
1. **A production secrets-management service is reachable from the public internet.** `/v1/sys/health` and
   `/v1/sys/seal-status` are unauthenticated *by design* (for LB/monitoring), but their reachability from an
   arbitrary host proves Vault's full API surface (incl. `/v1/auth/*` login endpoints) is **not network-restricted
   / IP-allowlisted / mTLS-gated**. Best practice is to keep Vault off the public internet.
2. **Outdated version — `1.16.2` (build 2024-04-22), OSS.** Later 1.16.x releases fixed real CVEs, the version is
   now exactly matchable by an attacker:
   - **CVE-2024-5798** (fixed **1.16.3**) — JWT `aud`/bound-claim validation flaw: an invalid login could succeed
     when it should be rejected. Directly relevant *if* this Vault exposes JWT/OIDC auth.
   - **CVE-2024-6468** (fixed 1.16.6) — DoS via crafted requests on the TCP listener.
   - Multiple later fixes (1.16.6 → 1.16.22 line) not present.
3. Also discloses `cluster_id`, `cluster_name`, unseal quorum (`t:2, n:18`), storage backend (`raft`), and precise
   build date — recon that aids targeting.

**Not done (deliberately):** no attempt to exploit CVE-2024-5798 or any auth endpoint — that would exceed
non-destructive PoC on a production secrets store. The finding is *exposure + outdated version*, with CVEs cited as
risk, not demonstrated.

**Honest severity & triage expectation:** **Low–Medium** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N ≈ 5.3,
info-disclosure framing). Realistic outcomes: accepted as a hardening/Low finding, **or closed as by-design /
known / accepted-risk** (the health endpoints are intended to be unauth, and the host is intentionally in DNS).
The strongest framing is "internet-exposed secrets manager + outdated version missing an auth-validation CVE fix →
network-restrict and upgrade." Do **not** oversell it.

**Remediation to propose:** restrict `vault.algolia.net` to internal networks / VPN / IP-allowlist (or mTLS);
upgrade Vault to a current 1.16.x patch (≥1.16.22) or newer line; if JWT/OIDC auth is configured, prioritize the
CVE-2024-5798 fix.

**Dedup check:** compare against disclosed reports for "Vault", "exposed infrastructure", version disclosure before
submitting (see `../09-disclosed-bugs-and-dedup.md`). Given the report volume on this program, an exposed-infra
report may already exist — search first.

**Sources:** HashiCorp CVE list — cvedetails.com/vulnerability-list/vendor_id-16814/product_id-70468 ;
Vault CHANGELOG — github.com/hashicorp/vault/blob/main/CHANGELOG.md ; HCSEC advisories (support.hashicorp.com).

### Deep read-only enumeration update (2026-09-25) → severity raised to Medium
Further unauthenticated, read-only enumeration (no auth attempts, no exploitation) found the exposure is broader
than version disclosure, and confirmed the CVE precondition:
- `GET /v1/sys/leader` → 200: leaks internal hostname **`hashicorp-vault-02.algolia.internal`** (ports 8200/8201),
  HA state, raft committed/applied indices.
- `GET /v1/sys/internal/ui/mounts` → 200: unauthenticated **auth-method enumeration** — `oidc/` "**Okta OIDC**"
  enabled (secret engines correctly filtered/empty).
- `GET /v1/identity/oidc/.well-known/openid-configuration` + `/keys` → 200: Vault's OIDC identity provider enabled
  (issuer + public JWKS; the JWKS is public by design).
- Properly protected: `/v1/sys/ha-status`, `/v1/sys/internal/ui/resultant-acl` → `permission denied`;
  `/v1/sys/metrics` → 404.

**Why this raises severity:** CVE-2024-5798 affects the **JWT/OIDC auth method**, which is now **confirmed enabled**
on this internet-reachable v1.16.2 instance. The vulnerable component is live, not hypothetical → credible
**Medium** (ceiling High/Critical *iff* exploitable against the OIDC role config, which was NOT tested). See
`report-vault-exposure.md` for the full write-up. **Active probing stopped here** — exploiting the auth-bypass CVE
on a production secrets manager is out of bounds for authorized non-destructive testing.
